# Ruta iOS — 3-day port plan

> **Status (end of sprint): delivered.** Core protocol, session, rides, navigation, battery and
> all screens are done; byte-exact Android test vectors pass (`swift run RutaTests`), screens are
> verified via `swift run RutaSnapshot`, and the iOS app project (`Ruta.xcodeproj`, XcodeGen spec
> committed) builds in CI. Open items are hardware-only: the PIN pairing flow, background BLE and
> non-VX2 models — the friend runs [`docs/TESTING.md`](TESTING.md).

Goal: an iOS Swift rebuild of [CODESURGEN/ruta](https://github.com/CODESURGEN/ruta) for one rider,
built without an iPhone or scooter on hand.

## Constraints

- No iPhone, no scooter. Everything must be provable in a simulator, a macOS build, or unit tests.
- No Xcode locally: ~11 GB free, Xcode needs 25–40 GB. Use `swift build` / `swift test` with the
  installed Command Line Tools, and a GitHub Actions macOS runner for the real iOS build.
- 2–3 days. That buys a complete, compiling app, not a hardware-validated one.

## What "done" means for this sprint

Works without hardware:

- Byte-exact BLE protocol (frames built and parsed) with the Android test vectors ported to Swift.
- CoreBluetooth transport, connection state machine, reconnect, diagnostics log.
- SwiftUI app: onboarding, cluster/home, rides, battery/insights, settings, diagnostics.
- Fake scooter transport for the simulator and macOS preview.
- iOS project generated by XcodeGen + CI that builds a simulator app and an unsigned `.ipa`.

Stays unproven until a real iPhone meets a real TCU:

- Pairing with the scooter PIN.
- Background BLE while the phone is locked.
- Scooter model compatibility (repo tested on VX2).

Out of scope, because iOS has no equivalent:

- Reading Google Maps' navigation notification → replace later with MapKit guidance.
- Caller name/number, answer/reject from the handlebar, missed calls.
- Notification counts, "who messaged".
- Music metadata from other apps without private `MediaRemote` APIs.

## Day 1

1. Repo scaffold, Swift package (`RutaCore` + `RutaUI` + macOS preview), CI skeleton.
2. Port `TcuProtocol.kt`, `IcbtText`, parsers, and every case in `tests/IcbtProtocolTest.kt`.
   `swift test` must be green before moving on.
3. Port `RideMath.kt`, `Range.kt`, `NavCountdown.kt`, `RoadNames.kt` and their tests.
4. CoreBluetooth transport + fake transport + diagnostics ring buffer.

## Day 2

1. SwiftUI shell, theme tokens, cluster/home screen.
2. Onboarding and connection flow (scan by `HMC_`, saved scooter, PIN explanation).
3. Ride recording, storage, battery/insights, settings, alerts.
4. macOS preview runs; every screen reachable with the fake scooter.

## Day 3

1. XcodeGen iOS target, Info.plist, background modes, entitlements-free signing setup.
2. CI workflow: build for simulator, run tests, package unsigned `.ipa`.
3. Fix compile errors from CI, tag the build, write the friend-facing test guide.
4. Handoff: what to test first (nRF Connect pairing check, then the app), and how to read logs.

## Test strategy

- **Byte-exact:** port the Kotlin host tests one-for-one. They contain hex captured from a real VX2.
- **State machine:** fake transport that replays frames and simulates disconnects/pairing failures.
- **UI:** SwiftUI previews + macOS executable; simulator once Xcode/CI is available.
- **Hardware:** friend runs one build, exports the diagnostics log.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| iOS won't bond to the TCU PIN flow | Fatal | nRF Connect pre-flight on the friend's iPhone before the reveal |
| Background BLE throttled | Cluster stutters when locked | Event-driven writes on TCU frames, no timers |
| Friend's scooter isn't a VX2 | Unknown frames | Model/firmware banner, raw frame log |
| No local iOS compiler | Blind UI code | macOS preview + CI on every push |
| Free-account 7-day expiry | Annoying | TestFlight ($99) or AltStore refresh |
